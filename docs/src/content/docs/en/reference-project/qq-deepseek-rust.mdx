### QQ memory commands

```text
/memory
/remember I prefer concise answers
/forget 1
/forget all
/memory compact
/reset
```

/memory shows bounded summary, facts, and persistence state for the current session; /remember adds an explicit fact. /forget INDEX removes one fact and /forget all clears all memory. /reset clears summary and recent turns while keeping explicit facts; /stop only cancels pending results. A clear is durable only when persistence succeeds; an absent card is not reported as erased.

The authenticated web memory preview is at most 8 KiB and omits session keys and recent raw chat. Stop the bot and finish background operations before web edits to avoid racing model writes; this is not a complete memory-export feature.

### QQ image input

The official DeepSeek [Vision guide](https://api-docs.deepseek.com/guides/vision/) documents Flash image input; check the active model catalog rather than assuming every DeepSeek model supports it. The v0.5.0 QQ implementation accepts up to 2 JPEG, PNG, GIF, or WebP images per message, with an HTTPS URL of at most 4096 bytes and declared limits of 8 MiB and 8192 pixels per side. The ESP does not download or independently measure the image, so declared metadata is not content verification.

DeepSeek retrieves the image; the ESP submits bounded image content blocks. Signed attachment URLs do not enter long-term memory or ordinary logs. QQ URLs may expire or be inaccessible to DeepSeek; unsupported models or rejected inputs must be reported rather than presenting a text-only answer as image recognition.

### QQ remote access and feature boundaries

QQ buttons can open URLs, deliver callbacks, or send commands, but do not provide this project with a general HTTP tunnel into a LAN. Sending a 192.168.x.x link does not make the page externally reachable. [Official button reference](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/trans/msg-btn.html) Current remote status, LED, and memory operations use allow-listed QQ text commands; the web manager remains LAN-only with no public endpoint deployed.

OTA updates, full memory export, and account-quota management are not implemented and are outside this acceptance.

## v0.4.0: Natural-language tools and SD history retrieval

Say “Look up the official ESP32-S3 documentation”, “Read https://example.com/ and summarize it”, or “What comet plan did we discuss earlier?” The model chooses Search, Fetch, or SD history retrieval for the current session. Greetings and ordinary rewriting normally answer directly without an extra planning request. Tool selection is model-dependent and identical choices are not guaranteed for every wording.

Each request executes at most 2 tools sequentially, then disables tools for the final answer. Natural-language web results contribute at most 4 KiB of body text per call, encoded tool results at most 8 KiB, and serialized model requests at most 48 KiB. Existing overall deadlines, cancellation, and QQ reply deadlines still apply. Online calls use DeepSeek account quota; web and historical content remain untrusted reference data.

History is isolated by private user or group-plus-sender. Each session retains a ring of the latest 32 turns successfully saved to working memory; user text is clipped to 1024 bytes and assistant text to 2048 bytes at UTF-8 boundaries, with truncation marked. The sole SD owner reads and CRC-checks one record at a time and returns at most 3 snippets of 768 bytes each. There is no resident vector database or full-history RAM index. The existing 48 KiB working-cache budget is unchanged.

Use `/memory search KEYWORDS` to inspect matching snippets. `/reset` and `/forget all` also clear that session's archive, syncing the deletion watermark to both manifest slots before confirming success. Unavailable SD never produces a fake successful search; history_failed and related status expose archive write failures. Raw text already replaced by pre-upgrade summaries cannot be recovered. New archives accumulate from completed post-upgrade turns.

## v0.5.1: Small text attachments and media replies

Small QQ TXT, Markdown, CSV, JSON, log and common code files are read as untrusted references, never executed. Each message accepts at most two files, each at most 16 KiB and UTF-8 only. Raw files are not saved to SD; bounded text excerpts enter existing conversation memory. Each excerpt is at most 3 KiB, and JSON-escaped material remains inside the existing combined 4 KiB reference budget. Limits mark truncation; PDF/Word/video and untranscribed voice are never presented as understood.

Downloads accept only HTTPS QQ/qpic CDN URLs supplied as QQ attachments, with no redirects or QQ/DeepSeek credentials. The existing inference worker reads files sequentially, at most 20 seconds each, before opening the model connection. Actual bytes, declared size, UTF-8 and control characters are checked. Upload failure reports an error; final-send failure retains diagnostics. Account permission, URL accessibility and client rendering still require real tests.

Actual links in files or cards/quotes supplied with the current message can be natural-language Fetch targets, remaining untrusted and subject to existing tool-count, source and deadline limits. Typing and throttled streaming are covered in v0.6.0; interactive buttons remain unfinished.

## Build and connect

Start at the repository root with IDF_PATH pointing to an installed ESP-IDF v5.5.4, then load the SDK and espup environments. Application AGENTS.md and toolchain-versions.txt record the tools and development checks.

```sh
. "$IDF_PATH/export.sh"
. "$HOME/export-esp.sh"
cd application/qq_deepseek_rust
cargo +esp build --release --locked --features bot
```

A build without the bot feature omits QQ and model workers; independent modules still provide board, NVS, network, and management functions. Before flashing, verify the device, partition table, and recovery backup; avoid generic flashing operations that also overwrite unknown partitions.

Use the board CH340 serial connection at 115200 baud. Only one process may own the port at a time; close other monitors and serial terminals before running the tool below.

```sh
python tools/boardctl.py "status" "selftest" "nvs test" "wifi status"
```

The tool defaults to the known serial by-id path; use --port for another device. Since v0.2.0, firmware reports console.protocol=3 in status; replies still use QD2_REPLY / QD2_EVENT length-and-CRC frames, and the tool accepts legacy v0.1.0 replies; serial input is not echoed.

Serial captures confirmed SDK logs inside fragmented JSON, and complete writes alone still suffered stress truncation. r1 protocol=3 passed 120 concurrent-log and 100 network-recovery queries without query timeouts, each run safely recovering one damaged reply; the recorded 132/136-byte gaps remain unexplained. Mutations require ID, CRC, and a current boot guard, and the latest reply can be retransmitted for an identical ID/request without re-execution; duplicate nvs test advanced once, and old guards, missing guards, and raw mutations were rejected. Unguarded bootstrap permits only an exact read-only whitelist; use the matching boardctl, and distinguish passing protocol recovery from eliminating raw byte loss.

## Private configuration import

Fill in your configuration in .private/provision.json and set its permissions to 0600. Git ignores this directory; keep credentials out of source, public logs, and command-line arguments. Every field is required; the device assigns generation during import.

```json
{
  "version": 1,
  "generation": 0,
  "wifi_ssid": "YOUR_WIFI_SSID",
  "wifi_password": "YOUR_WIFI_PASSWORD",
  "deepseek_key": "YOUR_DEEPSEEK_API_KEY",
  "deepseek_model": "MODEL_FROM_CATALOG",
  "qq_app_id": "YOUR_QQ_APP_ID",
  "qq_app_secret": "YOUR_QQ_APP_SECRET",
  "allow_users": ["YOUR_USER_OPENID"],
  "allow_groups": []
}
```

Replace the placeholders with your configuration. QQ uses official Bot credentials and user openids; group messages also require the group openid in allow_groups, and an allowed group does not authorize an unlisted sender. Set the DeepSeek model to an ID available to the account.

```sh
chmod 700 .private
chmod 600 .private/provision.json
python tools/boardctl.py --config .private/provision.json --wait-online 90
```

The tool checks firmware identity before import and returns only redacted status. If the bot is running, issue bot stop and wait for it to stop before replacing configuration. Wi-Fi connects automatically at boot or after import; failures use retry backoff, and wifi status reports connectivity, IP, and synchronized time.

## LED control and basic diagnostics

The on-board LED is one WS2812 on GPIO48, driven with GRB data over RMT rather than ordinary GPIO switching. Channels are limited to 0 through 32; verify red, green, blue, and off at low brightness first.

```sh
python tools/boardctl.py --led-test
python tools/boardctl.py "led rgb 16 0 0" "led status"
python tools/boardctl.py "led off"
```

driver_applied is the last value successfully sent by the driver and does not replace physical observation. status also reports Flash, PSRAM, internal heap, stack margin, watchdog, and serial queue overruns; selftest runs hardware checks and reboot requests a restart.

## NVS and storage behavior

Configuration uses cfg0 and cfg1 slots in the qqds_v1 namespace. Only the inactive slot is written, and the active configuration changes after validation, commit, and successful readback; the other slot is still checked when one is damaged. Initialization errors never trigger automatic NVS erasure.

nvs test writes a new probe sequence and random value; compare nvs.probe from status before and after reboot to verify persistence. Configuration and LED control do not depend on SD. v0.2.0 kept short history only in RAM; v0.3.0 adds the SD memory and per-session on-demand restoration described below. The new format does not scan or import legacy sessions.

## QQ echo and DeepSeek

These commands are available only in bot-enabled firmware. Starting a service requires connected Wi-Fi, synchronized time, and configured QQ credentials and allow lists. Validate QQ and LED control in echo mode before switching to model mode.

```sh
python tools/boardctl.py "bot start echo" "bot status"
python tools/boardctl.py "bot stop"
python tools/boardctl.py "deepseek probe"
python tools/boardctl.py "deepseek status"
python tools/boardctl.py "bot start deepseek"
```

bot stop is cooperative; before switching, wait for active_workers in bot status to reach 0, as a retained bot status object does not mean threads are still running. Local shutdown still occurs if persisting the off state to NVS fails; the error reply explains that autostart after reboot may remain enabled.

deepseek probe checks authentication and the model catalog; deepseek test starts a short inference and uses API quota. Diagnostics run in the background, with completion available through deepseek status. They can run alongside EchoOnly mode; stop DeepSeek mode first and wait for existing diagnostics or notifications to finish.

In an authorized QQ conversation, test /ping, /echo text, /status, /led on, /led off, /led rgb R G B, /led status, /reset, and /stop. Only model mode forwards ordinary text to DeepSeek; remote configuration, arbitrary GPIO access, and script execution are not exposed.

After an explicit successful start, the intended mode is saved in the separate bot_mode key. On reboot, hardware checks, Wi-Fi, and synchronized time precede service recovery; bot stop persists off, and a missing record defaults to off. v0.3.0 reads a session from available SD when it is next accessed; memory restoration and service autostart are separate acceptance checks.

The local bot notify-owner text command makes one explicit proactive notification attempt to the sole configured owner; inspect bot status or deepseek status for its result. It does not retry automatically, and neither reboot nor service autostart repeats the message. Run this command only when a notification is intended.

## LAN web management

v0.2.0 starts the manager after Wi-Fi connects. From the same LAN, open the HTTP address corresponding to wifi.ip in status; the page itself is public, while every /api/ status, configuration, and action request requires the management code.

```sh
python tools/boardctl.py "web pairing"
```

web pairing explicitly returns the management code only over the local serial port, never publicly through QQ or the web page. The code grants configuration access, so keep it private; the page stores it only for the current browser session, and “Lock” clears it. The current manager uses HTTP and should be accessed on a trusted LAN.

The page provides overview, connection settings, and diagnostics. r1 passed login, authentication, origin, size-limit, and AI checks; on the r3 device, Search continued while the operator switched to Overview, turned the LED on, stopped the bot, turned the LED off, and refreshed, then returned to all 3 sources intact. Empty error records correctly show no current errors, and HTTP hashes of all 3 static assets match source.

Stop the bot and wait for workers to exit before saving configuration. Reading configuration never returns stored passwords or keys; blank secret fields retain their existing values. Saves carry the current generation and reject stale versions, so reload before editing again; a Wi-Fi change may require finding the device on the new network, and saving alone does not re-enable the bot.

## SD card support

At startup, v0.2.0 makes one mount attempt on a dedicated worker. The board uses SDMMC slot1, 1-bit, and 20 MHz; mount failures do not block networking or chat, and never trigger formatting, repairs, or endless retries. There is no card-detect pin, so an error must not be interpreted as proof that no card is inserted.

The new firmware performs probes, listings, and diagnostics only under /sdcard/qq-deepseek/, without scanning, migrating, or deleting legacy directories. A 32 GB card reported 30,985,420,800 bytes and passed a 64-byte exclusive-write, sync, read/compare, and delete probe; after r1 GUI unmount, QQ, web, and Wi-Fi remained available and self-test reported sd_required=false, then remount, probe, and listing passed again. This does not establish physical no-card boot or integrity of every old file.

```sh
python tools/boardctl.py "sd status"
python tools/boardctl.py "sd test"
python tools/boardctl.py "sd list"
```

sd mount, sd unmount, sd test, and sd list run in the background. After each operation, wait for busy=false in sd status, inspect last_result and fault, and only then start another operation. Use sd unmount before removing the card; I/O failures or an operation deadline disable further access, and cleanup failures require reboot, while serial and web status remain available.

The Boot diagnostic log still contains only fixed events and numeric times and stops growing at 64 KiB. With user authorization, v0.3.0 separately stores sessions, facts, and summaries under /sdcard/qq-deepseek/memory/. Memory does not enter NVS, ordinary diagnostics, or public logs.

## DeepSeek Search and Fetch

Web tools call the official DeepSeek [Search / Fetch API](https://api-docs.deepseek.com/guides/search/) directly with the same DeepSeek key. In v0.4.0 ordinary text can request model-selected search, page reading, and current-session history retrieval; explicit commands remain available.

```text
/search ESP32-S3 official documentation
/fetch https://api-docs.deepseek.com/guides/search/
搜索：ESP32-S3 官方文档
抓取：https://api-docs.deepseek.com/guides/search/
```

The Chinese “联网搜索” prefix is also supported. The QQ path first retrieves search summaries or page Markdown, then asks the model to summarize and appends actual source links returned for that request; web tools and serial diagnostics return sources plus a bounded preview. Retrieval is not independent verification of a page, and instructions inside a page are not treated as device commands.

Search queries are limited to 128 Unicode characters; Fetch requires an HTTP/HTTPS host address and rejects clearly local addresses and URLs containing credentials, with body, context, and total-duration limits. Oversized material is explicitly truncated or rejected, and empty results, API rejections, and timeouts are reported; calls consume DeepSeek account quota.

```sh
python tools/boardctl.py "deepseek search ESP32-S3 official documentation"
python tools/boardctl.py "deepseek fetch https://api-docs.deepseek.com/guides/search/"
python tools/boardctl.py "deepseek status"
```

Direct diagnostics can run in EchoOnly mode; stop DeepSeek mode first and run one diagnostic at a time. QQ conversation still follows the existing allow lists, cancellation, message deadlines, and bounded short-history rules.

## Errors and reconnect records

v0.1.0 reproduced a normal op7 reconnect being misclassified as a Transport error; the original 6/7 cumulative errors cannot be attributed individually. v0.2.0 separately tracks reconnects, AI counts, and the latest 16 recent_errors, which reset with runtime recreation. r3 passed key stop-path device regression, but exceptional SDK-hang timeout handling, complete QQ retrieval Q&A, and sustained operation remain pending; zero counters and short tests are not substitutes.

The r3 cleanup thread exclusively owns SDK resources and retires them through stop→destroy; the gateway waits at most 12 seconds, then latches a cleanup error and reboot-required state without creating another connection in that boot. After 4 seconds offline and recovery, the device stopped in 1.6901 seconds with workers=0, cleanup_failed=false, and cleanup_active=false, then Echo reached QQ READY. The SDK can still hang internally, and the exceptional cleanup-timeout branch has not been manually injected.
