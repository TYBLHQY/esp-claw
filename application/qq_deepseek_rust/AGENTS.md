# Rust QQ DeepSeek Firmware

This directory is an independent Rust std application for the GOOUUU ESP32-S3-CAM N16R8. It uses ESP-IDF drivers and TLS, with no dependency on the legacy ESP-Claw runtime, Board Manager, Lua, or reusable `components/` tree. The user's Rust requirement overrides the old application's C implementation conventions here. Keep unrelated legacy changes intact.

## Build and Test

Use the fixed versions in `toolchain-versions.txt`, `Cargo.lock`, and `components_esp32s3.lock`. ESP-IDF is **v5.5.4**, the Rust target is `xtensa-esp32s3-espidf`, and the rustup toolchain is `esp`. Do not update dependencies or regenerate a different partition table as a routine build fix.

From the repository root on this host:

```bash
. /path/to/esp-idf-v5.5.4/export.sh
. "$HOME/export-esp.sh"
cd application/qq_deepseek_rust
cargo +esp build --release --locked --features bot
```

Omit `--features bot` for the hardware-only build. The ESP-IDF exports provide the existing Python, C toolchain, and flashing tools; the espup export supplies the matching libclang path. Install the versions recorded in `toolchain-versions.txt` when setting up another host.

Run host protocol tests from this directory, with an explicit host target so Cargo does not select Xtensa:

```bash
cargo +stable test -p qq-deepseek-core --locked --target x86_64-unknown-linux-gnu
cargo +stable clippy -p qq-deepseek-core --locked --target x86_64-unknown-linux-gnu --all-targets -- -D warnings
```

Keep firmware builds separate from host tests. A successful cross-build is not device acceptance.

## Ownership and Hardware

- `src/platform/` owns SDK handles, fixed board wiring, diagnostics, NVS, Wi-Fi, and the SD owner. `crates/protocol-core/` contains host-testable configuration, record, command, SSE, and bounded Search/Fetch logic.
- GPIO48 is one WS2812 with GRB order. Its RMT channel, encoder, and heap payload have one owner. RGB channels are limited to 32. A driver result does not establish the observed color.
- UART0 is the CH340 console at 115200. Exactly one host process may own its serial port; stop monitors before using `tools/boardctl.py` or esptool. Use the discovered by-id device path rather than assuming a port number.
- Emit structured diagnostics through `platform::console::reply/event`, using complete QD2 length/CRC frames and the shared UART driver/VFS write lock. Never return to fragmented `println!` JSON output: C SDK logs were observed inside those fragments. Complete writes alone are not sufficient evidence of reliable delivery: network-loss stress still captured one 4096-byte truncation after 120 ordinary queries passed.
- The latest UART contract advertises `console.protocol=3`: require request ID, CRC, and the current boot guard for every non-whitelisted operation. Only the exact side-effect-free bootstrap query whitelist may run without these guards. Cache the latest reply; the same ID and identical request may retransmit that reply without re-executing, while a conflicting ID payload or an old boot guard must be rejected. Keep one serial request in flight; this is a single-entry response cache, not persistent general-purpose deduplication. CRC detects corruption and is not authentication. Use the matching boardctl and preserve legacy reply parsing.
- Keep QQ heartbeat, model requests, and board control independently scheduled. Never perform network or NVS operations in the WebSocket callback or while holding a shared state lock.
- Never free a C handle or mutate an in-flight payload from another task. Check SDK returns, allocation failures, task startup failures, and bounded shutdown results.
- Concurrent QQ, model, and Search TLS work uses the SDK's official `CONFIG_MBEDTLS_EXTERNAL_MEM_ALLOC=y` support. Earlier Search testing reduced internal free RAM to 2,267 bytes; r1 mixed Search/Fetch testing after the PSRAM change measured a 48,359-byte minimum, while the distinct r3 mixed round measured 44,731 bytes. Preserve the setting and record the round for each measurement; none is sustained-operation acceptance.
- The camera remains disabled. SDMMC slot1 uses CLK39/CMD38/D0 40 in 1-bit mode at 20 MHz, with no card-detect or write-protect GPIO. Only the dedicated SD worker may initialize, mount, access, or unmount its C handle. Main-loop startup may enqueue one background mount; never turn failure into automatic formatting, repair, or endless retries.
- `src/web.rs` owns the bounded ESP-IDF HTTP server and static `src/web_assets/`; `src/management.rs` bridges it to the main owner through bounded commands and cached snapshots. HTTP callbacks never manipulate device handles, NVS, SD, or remote API connections directly.

## Configuration and Recovery

- NVS initialization must not erase on error: use `EspDefaultNvsPartition::take_with(false)`. Never automatically erase NVS, format SD, or wipe Flash to hide a failure.
- Configurations use validated `cfg0`/`cfg1` records in `qqds_v1`. Write only the inactive slot, commit and read back before publishing. Check the other slot if one is invalid. Generation is device-owned.
- The separate `bot_mode` key holds user intent: 0 off, 1 echo, 2 DeepSeek. Missing means off. Persist it only on explicit user mode commands, not each reconnect.
- `bot stop` must signal local workers and clear in-memory desired mode before attempting the NVS write. On persistence failure, report that reboot autostart may still be enabled. A retained bot object is not a running worker: wait for `active_workers == 0` before switching modes.
- Direct `deepseek probe`/`deepseek test` diagnostics may run in EchoOnly mode, but not alongside a DeepSeek model worker or another active diagnostic/notification. `bot notify-owner` is an explicit, single notification attempt with no automatic retry or replay on reboot; never add it to startup or routine validation without user intent to send.
- v0.3.0 adds user-authorized persistent conversation memory under `/sdcard/qq-deepseek/memory/`; RAM fallback remains available without a card. Keep the v0.2.0 RAM-only baseline separate from new-version restart-recovery acceptance. Never silently overwrite unknown disk records with offline RAM history.
- SD read/write probes, listings, and optional journals are restricted to `/sdcard/qq-deepseek/`; preserve legacy card paths. A probe creates a unique file exclusively, syncs, reads back, compares, and deletes it. Record numeric stage failures; do not misreport a mount failure as proof of card absence. After a visible operation deadline or I/O failure, disable more I/O until explicit cleanup; failed cleanup requires reboot and must not reuse an uncertain C pointer.
- The diagnostic journal remains restricted to typed Boot events and numeric time, with no chat/keys and a 64 KiB growth limit. User-authorized v0.3.0 memory is a separate file format and directory; do not put conversation text into the general journal, NVS, routine logs, or public snapshots.
- Every `/api/` route requires the LAN management token, including status and configuration reads; static assets alone may be public. Only explicit local UART `web pairing` may disclose the token. Keep it out of routine logs, QQ, snapshots, and public documentation. Web configuration reads expose no stored secrets; blank secret fields retain current values, and stale generation writes are rejected. Stop the bot and finish diagnostics before configuration changes.
- Search and Fetch use `https://api.deepseek.com/v1/tools/search` and `/v1/tools/fetch`, respectively, with the configured DeepSeek bearer key. The ESP must never fetch arbitrary target URLs itself. The user authorized natural-language tool selection in v0.4.0. Ordinary text may invoke model-selected search_web/fetch_page/recall_history; explicit commands remain supported. Cap total tool executions at two per request, serialize execution, disable further tools for the final completion, cap each natural web context at 4 KiB and encoded tool result at 8 KiB, and cap serialized model requests at 48 KiB while writing, not after an unbounded allocation. Fetch targets must appear in the current user input, material actually supplied in the current QQ message (including cards/files), or real sources returned during this request. Summaries and image diagnostics do not enable tools. Treat retrieved text as untrusted data, preserve only real returned source URLs, and enforce URL, query, response, context, cancellation, and overall-time bounds.
- `.private/` and `target/` are ignored. Keep provisioning JSON, sensitive captures, device images, and credentials in private files with mode 0600; never commit or print them. Do not compile secrets into a redistributable binary.
- `tools/boardctl.py --config .private/provision.json` imports credentials without putting them in command arguments or echoing them. Its identity check must succeed first; stop the bot before replacing configuration.
- Before flashing, identify the device and read `CONFIG_PARTITION_TABLE_OFFSET` from the pinned/generated SDK configuration: it is **0x9000**, not 0x8000. A stale unused factory-layout table remains at 0x8000 and must never guide deployment. Read the active table at 0x9000 and compare it with `partitions.csv` and the verified backup. The active ota_0 application begins at 0x20000; NVS begins at 0xa000. Run validation and flashing sequentially with checked subprocess returns so a failed check cannot fall through to a write. Preserve the already-verified full backup and record exactly which partitions are written. Do not assume a generic full-flash command preserves the old table or NVS.
- Never run esptool, a serial monitor, and boardctl concurrently. A serial open or RTS/DTR change can reset the board; control that behavior explicitly.

## v0.3.0 Memory and Vision

v0.3.0 is deployed and has the explicitly scoped device evidence below. Preserve the v0.2.0 r3 rollback image and unrelated legacy C edits; do not merge historical or bot-stopped measurements into a new QQ-concurrency acceptance claim.

- CopilotLee is the trusted assistant identity. Model replies follow the latest original natural-language user input; URL/image/OCR/page wrappers and stored summaries do not establish a language preference. The management UI currently remains Chinese. Memory, retrieved pages, and image content stay untrusted data, never interpolated into system policy.
- Only the SD owner reads/writes memory. `MemoryClient` is a cloneable bounded request handle; its blocking calls belong on background workers, not the board loop or SDK callback. The 3-second client deadline leaves the sole owner alive, quarantines uncertain I/O, and never reports an unknown write as saved. Recovered access must reload and compare revisions before mutation.
- Memory uses two CRC/revision slots, inactive-slot sync and readback, key validation, and optimistic revision checks. A damaged slot may fall back; two damaged slots, collisions, and symlinks are not silently replaced. A confirmed reset mirrors its tombstone into both slots, so callers must not assume a reset increments revision only once. This is record-level recovery, not proof against arbitrary FAT or power-loss corruption.
- Limits are 32 persisted sessions, 48 KiB JSON payload per record, 16 explicit facts of 512 UTF-8 bytes, a 4 KiB summary, and at most 8 recent turns/32 KiB. The RAM text-cache budget is 48 KiB. Unknown stored history must survive offline RAM conflicts; dirty eviction and failed saves must remain visible. Validate a replacement before committing it so a failed summary cannot leave an unbounded invalid record.
- Summarize older completed turns after 6 turns or byte pressure, normally retaining the latest 2. Only a complete valid summary replaces source turns; failure leaves the previous record intact. Summary calls use API quota. Never promote assistant speculation into user facts, execute instructions from memory, or retain credentials in generated summaries.
- QQ exposes `/memory`, `/remember TEXT`, `/forget INDEX|all`, `/memory compact`, and `/reset`; reset clears summary/recent turns but preserves explicit facts. `/stop` only cancels pending results. Report actual durability on a clear/save; an absent or failed card is not an erased card. Authenticated web edits require the bot stopped and background work finished. The <=8 KiB preview omits session keys and recent raw chat; it is not full export. QQ `/status` must omit private diagnostic results.
- Current official DeepSeek Flash supports images, this account's model catalog declares text/image input, and the ESP passed real OCR using a small diagnostic data URI; do not assume every model does or call this a QQ CDN end-to-end test. QQ accepts one image, HTTPS URL <=4096 bytes, JPEG/PNG/GIF/WebP, declared <=8 MiB and <=8192 pixels per side. The ESP does not download or independently measure image bytes/dimensions; DeepSeek retrieves the URL. Never store signed image URLs in memory/logs. Image-only messages remain replyable, and unsupported models/expired URLs cannot be presented as successful vision.
- QQ Gateway/buttons are not a generic LAN HTTP tunnel. Text commands support allow-listed remote control; the web manager remains LAN-only, with no public endpoint deployed. OTA, full memory export, and account-quota management are not implemented. Real SD persistence/restart/automatic summaries and diagnostic image OCR passed the v0.3.0 round below. True QQ attachment end-to-end recognition, physical no-card boot, and sustained operation remain pending.
